## 1. 三级滤波为什么要自己写，不调 IP 核

**提示词**：为什么要自己写无乘法去掉直流的滤波算法，不直接调用已有的 IP 核？

**模型回答**：先纠正提问的前提 —— 三级里只有一级有现成 IP 核。

| 级 | Vivado 免费 IP 库里有吗 |
|---|---|
| 直流阻断（一阶高通） | **没有**。它就是 3 行，没人为这个做 IP |
| 50 Hz 陷波（二阶 IIR） | **没有**。AMD 不提供通用 IIR 核 |
| 40 Hz 低通（FIR） | **有，FIR Compiler，而且很好用** |

所以真正的问题只有一个：**FIR 这一级要不要用 FIR Compiler。**

模型没有贬低 IP 核，而是先列了它的优势：自动对称折叠、自动时分复用、
自动 DSP 打包，资源通常比手写更省；Fmax 更高，时序更好收敛；
经过大量验证。并明确说明：**对一个真实产品项目，这一级会直接用 IP 核。**

不用的理由只针对本赛道：
- §3.3.1.1 初级组考察"逻辑设计、状态机、时序约束、接口协议等基本 FPGA 设计能力"，
  PL 侧若全是"例化 IP、连线"，可展示的自有设计很少
- §3.3.5.5"性能与资源优化 20 分"要优化过程，IP 核是黑盒，
  只能调配置参数，无法展示"加了这条 pragma，II 从 3 降到 1"
- 手写 HLS 的 C 仿真就是普通 C++，几秒跑完 60 秒数据直接对 `golden_float.txt`；
  IP 核只能走 RTL 仿真，一次几分钟，阶段 1 的快速迭代做不了

**最终结论不是"绕开 IP 核"，而是把它当基线**：手写 HLS 做主实现，
另做一版 FIR Compiler 的对比，报告里出一张"手写 vs 官方 IP：
资源 / Fmax / 延迟"的表。这样同时满足 §3.3.4"给出与基线的对比"，
并说明是**有依据地做了选择**，而不是不知道 IP 核的存在。

## 2. 这个问题顺带暴露出架构错了两个数量级

这是本阶段最严重的一个错误，而且**不是用户问出来的，是模型在回答时自己算出来的**。

**原先 `design_phase1.md` 里写的**：

> 每通道 21 个乘法器，8 通道 = 168 个 DSP48，占 XC7Z020 的 76%

**算一下时间预算就知道不对**：

```
采样率     500 SPS
时钟       100 MHz
每个采样周期 = 1e8 / 500 = 200,000 个时钟周期

8 通道每采样周期需要的乘法次数 = 21 × 8 = 168 次
```

**200,000 个周期里只需要做 168 次乘法。** 一个 DSP48 按每周期一次算，
占用率 **0.084%**。

也就是说一个 DSP 就够，原方案规划了 168 个 —— **差两个数量级**。

**为什么这个错误特别致命**：它正撞在评分细则的反面。§3.3.4 原文

> 合理使用片上资源，**避免以显著的资源代价换取有限的性能收益**

全并行架构在 500 SPS 下就是这条的反面教材。评委一算时间预算就看出来。

| | 全并行（原方案） | 时分复用（改后） |
|---|---|---|
| DSP48 | 168 | **1～2** |
| 支持通道数 | 8（受 220 个 DSP 限制） | 几十路 |
| 评分表现 | 踩"资源代价"这条 | 正面案例 |

**而且改后的说法是个更好的故事**："识别出采样率只有 500 SPS、
时钟 100 MHz，有 200,000 个周期的裕量，因此采用资源共享架构，
用 1 个 DSP 完成 8 通道 21 阶滤波" —— 比"堆了 168 个 DSP"有说服力得多。

**修正已落地**，现在 `src/hls/ecg_filter_coef.h` 开头写的是：

```
// 每通道每采样点的乘法**次数**：0 + 5 + 16 = 21
// 注意这是次数不是乘法器个数：500 SPS 下每个采样周期有 200,000 个 100MHz 时钟，
// 8 通道共 168 次乘法，一个 DSP48 时分复用即可（占用率 0.08%）。
```

实现手段：`#pragma HLS ALLOCATION` 限制乘法器实例数。

**这条的教训**：算资源时**必须先算时间预算**。
"每个采样点要 21 次乘法"和"需要 21 个乘法器"是两件完全不同的事，
中间差的就是采样周期里有多少个时钟。低采样率的信号处理题
几乎永远应该做资源共享，而**把"次数"误当成"个数"是一个会写进报告的错**。
→ 写进 `skill/pitfalls.md` 和 `skill/README.md`

## 3. ADC 码与物理电压的换算

**提示词**：`LSB_UV = 48.081e-3` 这行什么意思？这个数怎么得到的？

**模型回答**：ADS1292 输出的是整数码，本身没有单位。`LSB_UV` 是换算尺上的一格：

```
LSB = VREF / (gain × (2²³ − 1)) = 2.42 / (6 × 8388607) = 48.081 nV
```

两个容易错的点：

**① 单位。** 写成 `48.081e-3`，单位是 µV，即 **48.081 nV** ——
名字叫 `LSB_UV` 是"以 µV 为单位的 LSB"，不是等于 48 µV，差一千倍。

**② 它是"电极上"的一格，不是 ADC 内部的。** ADS1292 内部有 6 倍 PGA，
计算时**已经把增益除掉了**，所以可以直接拿它换算成人身上的电压，
中间不用再管放大器。

**为什么必须有这一行**：脚本里一切计算都在**码**的域里做（因为硬件就是这么算的），
但判断好坏必须用**电压** —— "残留漂移 0.17 mV"、"工频 224 µV"都是这么换出来的。
没有它，结论只能说成"残留 3600 个码"，没法和医学上的 mV 标准对比。

## 4. 讲解方式的转折：用户说"全看不懂"

当天最后一条用户反馈是三个字：**"全看不懂"**。

**起因**：模型解释 LSB 推导时给了一段密集的数字推演
（多个中间量、单位换算、位宽关系堆在一起），用户完全没接上。

**这不是用户的问题，是模型选错了讲解密度。**
前期学习阶段要建立的是直觉，而"把所有精确数字一次摆全"恰恰会盖住直觉。

**调整后的做法**（次日用户回"通了"验证有效）：
- 先给一个日常类比，再落到数字
- 一次只讲一个概念，讲完等反馈
- 具体数字只在"它本身就是结论"的地方出现，不做数字表格
- 段落短，不超过三四行

**这条属于提示词工作流而不是技术经验**，但它对项目进度的影响比任何单个技术点都大 ——
看不懂就学不下去，学不下去就只能照抄模型给的代码，
而 §3.3.3.1 要的是"协作"不是"代拍"。
→ 写进 `skill/README.md` 的"与大模型协作的节奏"一节
