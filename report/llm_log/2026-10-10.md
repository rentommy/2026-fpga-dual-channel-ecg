## 1. `>> k` 就是那个除法

**提示词**：`step = 1.0 / (1 << k)` 这一步除法就能用吗？在硬件上如何实现这个除法？

**模型回答**：`>> 7` **就是**那个除法。一个数在硬件里是一排导线，
"右移 7 位"的意思是把第 7 号线接到原来第 0 号线的位置 ——
**没有门电路、不花时间、不占 DSP**。

但这只在除数是 **2 的幂**时成立。这正是选 1/128 而不是"理想值"1/159.2 的原因：

```
fc = fs / (2π · 2^k)      k 只能取整数
k=6 → 1.243 Hz
k=7 → 0.622 Hz   ← 选它
k=8 → 0.311 Hz
```

截止频率不是设计出来的，是**被动接受**的 —— 代价是 0.622 Hz 而不是原来的 0.5 Hz。
换来的是整条直流阻断**零乘法器**。

**模型主动追加的坑**：心电数据是**有符号**的，所以
- Verilog 必须用 `signed` + `>>>`（算术右移）
- HLS 必须用 `ap_int<N>`，不能用 `ap_uint<N>`

逻辑右移会把每个负样本变成一个巨大的正数。
而实测直流失调是 **−3.942 mV**，**绝大多数样本都是负的** ——
这个错误会让输出完全失效，但在"只看小信号"的测试里可能不暴露。
→ 写进 `skill/pitfalls.md`

## 2. 为什么不用 FPGA 仿真软件来做这些验证

**提示词**：这些 py 的验证程序为什么不用 fpga 的仿真软件去验证？

**模型回答**：因为这两件事回答的是**不同的问题**。

| | 回答什么 | 代价 |
|---|---|---|
| Python 脚本 | 滤波器**该是什么样**（结构、参数、位宽） | 几秒 |
| HLS C 仿真 | **写出来的定点代码**对不对 | 几秒～几十秒 |
| RTL 仿真 | **综合出来的硬件**和代码一致吗 | 几分钟 |
| 上板实测 | 真实硬件在真实数据上行不行 | 分钟级 + 硬件 |

参数阶段要扫几十种组合（k × Q × N × 级数），
每次都跑 RTL 仿真的话一天跑不完几轮。
**Python 阶段的产出是"定下来的参数 + 黄金参考文件"**，
它们正是后面三层验证的输入 —— 不是替代关系，是上游。

## 3. 参考实现里两个必须注意的 Python 细节

**提示词**：直流阻断函数为什么不用 `np.asarray(x, dtype=np.float64)` 创建数组？

**模型回答**：两个独立的原因。

**① `np.asarray` 在 dtype 已匹配时不复制。** 实测验证过：

```
x 被改了: [99.  2.  3.]
```

对 `np.asarray` 的返回值写入会**污染调用方的数组**。
`dc_block_shift` 要就地写 `y[n]`，所以必须用 `np.empty` 新建。

**② 黄金参考必须无条件 float64。** 如果跟随输入的 dtype（整型），
参考实现就会**悄悄复现硬件的截断**，从而失去参考的意义 ——
参考自己也犯同样的错，比出来差异为零，标尺就废了。

→ 两条都写进 `skill/pitfalls.md`

## 4. 群延迟

**提示词**：群延迟的公式就是 (N−1)/2 吗，里面的 N 什么意思？陷波器的群延迟呢？

**模型回答**：

`N` 是抽头数。(N−1)/2 就是**中心抽头的下标**，单位是采样点。
但这个公式**只对对称 FIR 成立** —— 它成立的前提是线性相位。

**陷波器的群延迟是随频率变的**，没有单一值：

| 频率 | 群延迟 |
|---|---|
| 0.5–20 Hz | 0.11 点（0.22 ms） |
| 40 Hz | 1.31 点（2.62 ms） |
| 50 Hz | 47.75 点（95.5 ms），但此处衰减已 −61.9 dB |

在心电频带内可忽略，所以头文件里只写了 `FIR_DELAY 15`，
没有为陷波器留延迟补偿。

**顺带定位了一个一直没解释清的现象**：
`evaluate_chains.py` 表里"原版改单向"的全局相关系数只有 **0.589**。
真凶是原版那个 **3 阶因果巴特沃斯 0.5–40 Hz 高通**：
0.5 Hz 处群延迟 403 点（806 ms），10 Hz 处只有 4.86 点（9.7 ms），
**相差 80 倍** —— 没有任何单一平移量能把它对齐，
所以全局相关系数在这里是失效指标（与 `2026-09-30.md` 第 2 条同一个结论）。

## 5. 一处前后矛盾被用户抓到

**用户提问**：那之前香橙派的上位机陷波器还用双向滤波？

**矛盾在哪**：模型一直在讲"零相移需要未来的数据，硬件做不到"，
但上位机的代码里**确实在用 `sosfiltfilt`**。用户发现这两句话对不上。

**澄清**：区别在**是否流式**。

- 上位机是把一段数据读进内存再滤，整段 6000 点都在手上 →
  "未来的数据"是现成的，`filtfilt` 可行
- FPGA 是逐样本流式处理，第 n 个样本到来时第 n+1 个还没产生 →
  物理上拿不到

（技术上 FPGA 也能用 BRAM 缓冲 6000 点再反向滤，
6000×24 bit ≈ 4 个 BRAM18，140 个里占得起。
但那意味着**每个结果要等 10 秒以上**，实时显示就没了。）

**这次澄清引出了一个更重要的发现**：
查 `汇报材料/任务程序/main.py` 发现，**模型是用 `filtfilt` 预处理的数据训练的**
（4 阶 Butterworth 0.5 Hz 高通 + 34 Hz 低通 + 陷波，全部 `filtfilt`）。
也就是说因果滤波的数据对模型来说是**域偏移**。

这条线索在 `2026-10-18.md` 第 3 条被量化证实，并直接决定了
"FPGA 实时链 + PS 推理链"两条通路的划分方案。

## 6. 当天其他问答

- `dc_block_fc(k, fs)` 的作用：由移位位数反算实际截止频率，
  用来回答"k 该取几"
- `__pycache__`：Python 自动生成的字节码缓存，可安全删除，应进 `.gitignore`
- `sys.stdout.reconfigure(encoding='utf-8')`：GBK 无法编码 `µ`(U+00B5)，
  而脚本要打印 "µV"，所以这行是**必需的**不是装饰
- `sys.path.insert(0, ...)`：插在最前会**遮蔽标准库**，
  所以 `src/ps/` 下绝不能出现与标准库同名的文件
