# 大模型协作补记 2026-10-21

补记日期：2026-10-23。协作方：用户与Claude；整理方：GPT／Codex。来源为旧对话TXT（原工作区引用：`../../旧的资料/最后可直接获取的对话记录.txt`，未随此公共候选发布）第53～1848行可见内容。对话跨午夜且界面时间与工具时间不完全一致；本条主要记录10-21晚间，10-22明确有工具日期的优化及导出单列于次日。

## 1. 用户把目标转向尽快跑通全流程

用户提出先完成全流程验证，询问是否应打开Vivado。模型说明先由HLS生成IP，再用Vivado搭系统，最后通过PYNQ加载并比对。最初还笼统提到AXI DMA，后续检查实际接口后改为HLS自己的两个AXI主口直接访问DDR，不需要额外DMA。

当前机器没有工具且空间不足；用户说明另有安装工具的电脑并已搬移项目。实际推进方式是模型提供命令、用户在另一台电脑执行并贴回输出。SSH等远程方案只被讨论，原转录没有成功建立远程连接的证据。

## 2. 把本机搜索结果误当成远端事实

多次搜索工具没有输出，模型据本机没有安装目录，判断用户可能仍在原笔记本操作。用户给出的机器名证明正在另一台机器，随后提供 `D:/AMDDesignTools/2026.1/Vitis/bin/vitis.vbs`，才准确定位安装。

问题在于把“模型能访问的机器”与“用户正在执行命令的机器”混为一谈。更有效的检查应该先确认执行主机，再根据真实安装路径定位启动器，而不是重复扩大搜索。

## 3. 新版批处理入口与脚本约定不同

安装目录列出Vitis、Vivado；没有独立 `vitis_hls.bat`，有 `vitis-run.bat`。通过实际 `--help` 和运行输出确认本机使用：

```text
vitis-run --mode hls --tcl <脚本>
```

最初模型反复称旧 `run_hls.tcl` 无须修改，随后实际遇到启动器注入的 `-run` 被旧脚本参数解析拒绝。尝试补丁后又用外层脚本清空 `argv` 再 `source`，流程才走到工程创建及C仿真。此处“旧接口完全不变”的判断被实际运行推翻。

用户粘贴命令还遇到换行变为 `<br/>`、命令被截断和中文乱码。后续改为逐条完整命令或生成脚本，并读取落盘内容检查。模型曾把“没匹配到”的提示反解释为补丁已成功，缺少直接依据；应以文件内容差异为准，不能靠文件大小变化推断所有代码均已正确修改。

## 4. C仿真链接失败：先排除假设，再收窄路径问题

工具识别了 `xc7z020clg400-1`，说明该安装具备目标器件支持。随后C仿真只编译测试平台，报 `undefined symbol: ecg_filter_top(...)`。

| 最初判断／尝试 | 实验结果与修正 |
|---|---|
| 怀疑 `-cflags` 影响设计文件清单 | 移除参数后仍只编译测试平台；该假设被否定 |
| 暂绕C仿真，直接综合 | 综合也报找不到源文件及design unit；故障不限于仿真 |
| 将绝对路径改成相对路径，继续旧工程流程 | 仍报 `Cannot find source file ../src/hls/...` |
| 使用 `open_component`，组件放工程根下 | 能分析两份设计文件，进入真正的代码检查 |
| 再把组件放入 `build/` | 路径失败重现，说明不只是命令名的问题 |

当时可用办法是使组件父目录与工作目录一致。这里记录的是本项目的可复现现象，不据此宣称所有2026.1安装、所有旧接口必然有同样缺陷。后续GPT用改变工作目录的方法保留 `build/` 组织方式，见10-22。

## 5. 普通整数测试没有覆盖ap_int的类型规则

设计文件真正进入编译后，首次遇到本项目代码问题：

```cpp
ecg_acc_t a = (v < 0) ? -v : v;
```

`v` 为 `ap_int<48>`，取负扩展为49位，三目表达式两边可互相转换而产生歧义。补丁显式将负值分支转换回 `ecg_acc_t`。旧对话记录本地普通整数测试重新通过、最大偏差仍约3.3码；远端曾漏执行补丁，又重复撞到相同错误，后续先打印实际源码确认。

原生整数分支通过，并不保证精确位宽分支可编译或语义相同。此次回归仅覆盖现有向量，不能进一步写成全部满量程输入都安全。

## 6. 第一次综合完成，却装不进目标芯片

日志显示生成RTL、HLS估计Fmax为136.99MHz。模型先根据乘法核明细粗估“三十几个DSP、约16%，可以装下”，读取完整汇总表后被否定：

| 项目 | 首版HLS估计 | XC7Z020可用 |
|---|---:|---:|
| DSP | 304 | 220 |
| LUT | 149887 | 53200 |
| FF | 66870 | 106400 |
| BRAM18K | 18 | 280 |

报告日期为10-21 23:55:58。304 DSP来自8份滤波核，每份约38 DSP；原先只看单实例明细，没有乘实例数量。DSP和LUT都超限，因此“综合命令成功”并不意味着系统可以实现。

定位出的结构问题是自动循环流水、按通道拆分的状态与函数复制共同导致大面积并行；而顶层 `ALLOCATION mul` 约束没有覆盖独立的 `ecg_filter_sample` 内部运算。用户原定的目标是利用500SPS的时间余量，让八通道共享算术资源，不需要这一轮多余的吞吐。

下一轮加入关闭自动流水、限制函数实例和限制内部乘法器三条指令。成功的工具日期已是10-22，接续见[次日日志](2026-10-22.md)。

## 7. 本段协作中的纠错与边界

| 问题 | 发现方式 | 后续原则 |
|---|---|---|
| 混淆模型本机与用户远端 | 用户提供主机标识及安装路径 | 环境事实必须绑定执行位置 |
| 断言旧脚本不用改 | 实际启动参数及路径错误 | 新版本兼容性用小实验确认 |
| 把链接失败归因于cflags | 对照实验仍失败 | 实验否定后明确撤销原因 |
| 认为open_component单独足够 | 嵌套目录重现失败 | 一次成功不等于归因完整 |
| 用g++结果替代ap_int检查 | 精确位宽编译暴露歧义 | 分开记录编译分支及证据 |
| 少算8份实例的资源 | 顶层汇总表超限 | 从全设计报告判断容量 |

当晚已得到首版RTL和明确的资源超限原因；尚没有可加载的比特流，也没有PYNQ验证。此前跳过C仿真是当时的推进选择，不是C仿真已通过，更不是免除后续硬件验证。
