# 大模型协作记录 2026-10-16

一个表述问题问了四遍 —— 模型解释不清的典型案例

---

## 1. 同一行代码问了四次

**代码**：

```python
sess = ort.InferenceSession(MODEL, providers=['CPUExecutionProvider'])
inp = sess.get_inputs()[0].name
classes = [l.strip() for l in open(CLASSES, encoding='utf-8') if l.strip()]
```

**用户的四次提问**：

1. 这是在做什么
2. `inp = sess.get_inputs()[0].name` 这行还是没看懂
3. 那就是读取模型输入格式名是吧
4. 读取模型输入格式的名子是吧

第 3、4 次用户给出的是**自己的理解**，两次都包含同一个偏差，
说明模型前两次的解释没有把关键区分讲出来。

---

## 2. 偏差在哪

用户说的是"输入**格式**的名字"，而这行读的是"输入**端口**的名字"。

**名称 / 类型 / 形状是三个独立的属性**：

| 属性 | 本行是否读取 | 本项目的值 |
|---|---|---|
| `.name` | **是** | 由模型文件决定，导出时定的 |
| `.type` | 否 | float32 |
| `.shape` | 否 | (1, 1, 3600) |

而且方向正好相反：

- **名字是从模型里查出来的** —— 因为导出 ONNX 时它被自动命名，
  代码写的时候不知道它叫什么
- **格式是代码里写死的** —— 下一行 `x.reshape(1, 1, 3600).astype(np.float32)`
  里那几个数是人填的，模型没告诉代码该填什么

所以这行的作用是：**问模型"你的输入口叫什么"，好把数据喂到正确的口上。**

`[0]` 是因为这个模型只有一个输入口，固定取第一个。
如果模型有多个输入（比如同时吃波形和元数据），
`sess.run()` 的字典就要填多个键，那时就不能写死 `[0]`。

---

## 3. 模型哪里讲错了

不是事实错误，是**解释顺序错了**。

前两次回答都是从"这行代码做了什么"讲起（读名字、索引 0、传给 run），
但用户卡住的点不在流程，而在**"为什么要去问模型，而不是直接写死"**。

**正确的切入点应该是先讲"不对称"**：
格式是代码写死的、名字是必须查的 —— 讲清这个不对称，
用户自然就明白这行为什么存在，也就不会把两者混成"输入格式的名字"。

**教训**：当用户复述的理解连续两次包含同一个偏差时，
**不要再把原解释换个说法重讲一遍**，
应该直接去讲那个被混淆的区分本身。
→ 写进 `skill/README.md` 的"与大模型协作的节奏"一节

## 4. 顺带记录：softmax 在这里的真实作用

同日讲解 `infer()` 时澄清的一点，与报告表述有关：

```python
e = np.exp(lo - lo.max())
p = e / e.sum()
k = int(np.argmax(p))
```

- `- lo.max()` 是**溢出保护**，数学上不改变结果
- `argmax(p) == argmax(lo)`，所以 **softmax 不影响分类结论**
- softmax 存在的唯一目的是产出那个可报告的百分比

**而那个百分比不是临床概率。** 它是模型在七个类别上的相对置信度，
受训练集类别比例影响，不能解读为"有 77.9% 的可能是房早"。
报告里引用这些数字时必须这样限定。
